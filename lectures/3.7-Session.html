Why the Command Line?

The last 100,000 crimes reported to Chicago police in 2025 (28MB)1:

wc -l data/crimes2025.csv                 # how many rows?
head -2 data/crimes2025.csv               # what are the columns?
cut -d, -f6 data/crimes2025.csv | sort | uniq -c | sort -rn | head

About two seconds for 100,000 rows, and no Python.

Download it beforehand. It took about 40 seconds on home broadband (16 Oct). Show the command, but don’t run it on the room’s wifi. The server sometimes returns an empty file with no error (it happened once on 16 Oct): check with wc -l and run it again if you get 0.

curl -L -o data/crimes2025.csv 'https://data.cityofchicago.org/resource/t7ek-mgzi.csv?$limit=100000&$order=date%20DESC'

This is the city’s API, as in the Python slide, with a limit and a fixed order (latest first: 30 July to 31 December 2025). Without $limit the API stops at 1,000 rows; with it set to 300,000 you get the whole year (238,150 rows, 69MB, about a minute). Don’t use the portal’s “Export” link (/api/views/.../rows.csv): it’s deprecated and the server says it stops on 22 December 2026.

This is the “Crimes - 2025” extract (t7ek-mgzi). The 2022 one the course used before is 9hwr-2zxp. The full “Crimes - 2001 to Present” (ijzp-q8t2) is too big to demo.

As of 22 Oct: top types THEFT 22,985, BATTERY 18,038, CRIMINAL DAMAGE 11,394. The API puts every field in quotes, so the output reads "THEFT". Records are revised daily, so re-run before class.

Why not Excel? 100,000 rows will open (Excel’s limit is 1,048,576; the 2001-to-present file is well over that). The real problem is what Excel does to the values: 66,222 of these rows have an IUCR crime code with a leading zero ("0560"), and Excel turns it into the number 560. beat ("0931") and district ("009") go the same way. Excel decides what the data mean as it opens the file, which is today’s question.

Is That Right?

grep -c '"HOMICIDE"' data/crimes2025.csv                    # 194
grep '"HOMICIDE"' data/crimes2025.csv | grep -c '"true"'    # arrests?

That’s not the number of homicides with an arrest: it’s 3 too many. Why?

awk -F, '{print NF}' data/crimes2025.csv | sort | uniq -c   # 22 columns?

Ask the room (pairs, 1 minute) before revealing: “Is 83 the number of homicides with an arrest?”

Why it’s wrong: arrest and domestic are both "true"/"false" columns next to each other. grep '"true"' also matches the 3 homicides with no arrest that were domestic.

The awk line: most rows have 22 fields, but about 1,800 have 23–25 (1,814 on 22 Oct), because descriptions like “AGG. DOMESTIC BATTERY - HANDS, FISTS, FEET, SERIOUS INJURY” contain commas inside quotes. cut -d, doesn’t know about quotes. Column 6 happens to come before the problem, so the first count was right, but only by luck.

Back to the week’s question: the storage format (CSV, and someone’s choice of description text) decides what a quick tool can see. The CLI is fast; it isn’t clever.

Two more data biography points if time:

  • updated_on: about 193,000 of the 238,150 rows for 2025 were revised in 2026. A ‘record’ is not fixed when it’s written.
  • The city says the data shouldn’t be used to compare over time, because classifications change after preliminary reporting. These are reports, as with GDELT.

From CSV to a Dict of Lists

import csv
import urllib.request

url = 'https://data.cityofchicago.org/resource/t7ek-mgzi.csv?$limit=20'

with urllib.request.urlopen(url) as f:
    rows = list(csv.reader(f.read().decode('utf-8').splitlines()))

header = rows[0]   # the column names
data   = rows[1:]  # a list of lists: one list per crime

crimes = {}        # a dict of lists: one list per column
for col in ['date', 'primary_type', 'block', 'arrest', 'latitude']:
    i = header.index(col)
    crimes[col] = []
    for row in data:
        crimes[col].append(row[i])

Copy and modify: this runs as-is in the SDS container, with no download. The ?$limit=20 asks the city’s API for just 20 rows. (The API’s column names are lower case with underscores, unlike the CSV export: primary_type, not Primary Type.)

We’ll see how this code works across later weeks. Focus on how the 3.2 list of lists becomes the 3.3 dict of lists. header.index(col) is the same trick as ds2['name'].index('Tokyo').

Break It

A reproducible sequence of interactions:

mkdir tmp
cd tmp
git init
echo "Test" > fileA.md
git add fileA.md
git commit -m "Added."
git rm fileA.md
git commit -m "Removed file."
ls                       # fileA.md has gone
git log --oneline        # find the hash before the removal
git checkout <hash>
ls                       # fileA.md is back

Live, in the SDS container: the Recovery slide from the Git video, done for real. Set up the repo beforehand (README → fileA.md → commit, as in the video).

Ask before running git checkout: “What will git status say now?”

Detached HEAD

git status               # HEAD detached at <hash>
git switch -             # back to the branch you were on

To bring one file back into the present:

git restore --source=<hash> fileA.md
git add fileA.md
git commit -m "Restored fileA.md"

This is the “getting back to HEAD” discussion that the Git video promises but never delivers.

git switch - works whether your branch is main or master. GitHub now defaults to main, but the video slides say master.

Commits on a Plane

CVS (1990), Subversion (2000) Git (2005)
Where is the history? On one central server In every copy
Commit offline? No Yes
GitHub is… (n/a) just another copy

So commit and push are different things.

The point the video doesn’t make: Git is peer-to-peer. Every clone is a complete repository, with the full history. GitHub is a copy that everyone has agreed to treat as the main one; Git itself doesn’t know that.

Can be brief, the history is optional. The history: CVS and then Subversion (“CVS done right”) were centralised: you needed the server to commit. The Linux kernel moved to BitKeeper, a proprietary distributed system, in 2002. In April 2005 the free licence was withdrawn after a dispute over reverse-engineering its protocol, and Linus Torvalds wrote Git in a matter of days to replace it. (Mercurial started that same month for the same reason.)

Why it’s weird: there’s no single ‘true’ copy, so pull and push are needed to make copies agree. Why it’s useful: you can commit on a plane, and the history survives if GitHub disappears. See: the great Moodle/PHP exploit of 21 October 2026!

This sets up the next slide: a commit on your laptop is not a backup until you push.

Pull, Then Push

git pull                 # get any changes from GitHub first
git add <notebook.ipynb>
git commit -m "What I did, and why"
git push                 # only now are you backed up

When asked for a password, GitHub wants a personal access token (or an SSH key), not your account password.

The video’s workflow slide leaves out pull, but the learning outcome includes it.

Why the command line rather than a GUI: it shows what’s happening behind the scenes. add and commit are separate steps, and a GUI usually hides that. The separation is the point: you choose what goes into the record.

Everyone should have a GitHub account by now. The first push from the command line is where the password prompt catches people out.

Link back to 3.6: in the group project you’ll be pulling and pushing to one repository with up to four other people, and the commit history is how we see who did what if a group falls out.

Spare question if time: “You commit, and then your laptop is stolen. Is your work on GitHub?” (No: all changes are local until pushed.) Story: the flatmate’s laptop.

A Commit Message Is Context

The way through this predicament is by considering context, a process that includes understanding the provenance and environment from which the data was collected […] ~ D’Ignazio and Klein (2020, 27)

git log is the provenance of your work. Write the message for the person who will read it in six months.

D’Ignazio and Klein’s “data biography” (p.24) asks five questions: Where did it come from? Who collected it? When? How was it collected? Why was it collected? A good commit history answers most of them for your own code. My margin note: “Something to think about for the assessment, perhaps?”

Bridge to the practical: the final commit of the notebook. Ask for a message that would make sense to a stranger.

Intro to the practical

Here’s what we’re covering:

  • Bedding in your Git/GitHub workflow. We’re trying to help you remember via repetition here and get good habits started early.
  • Lists and dictionaries are the ‘workhorse’ data structures of Python: you’ll use them all the time even once you know of other, more powerful ways to organise and manage data. You might, for instance, have a list of advanced data structures that you want to iterate over. Or a dictionary of parameters that you want to test in a model.
  • We’re also going to stretch your understanding of how these two data structures interrelate and, crucially, look at the DOL, which is analogous to how pandas — probably the single biggest reason Python dominates data science — manages and represents data to you.
